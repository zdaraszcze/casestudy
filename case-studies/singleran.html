Case study, telecom network operations

D&M for SingleRAN: one live view of the whole base station

Engineers who ran multi-technology base stations worked from text fault logs, command-line output, and their own memory of each site. As lead UX designer and researcher, I designed a browser console that draws the whole site as one live map, where every module shows its state and every alarm appears on the module that raised it.

Role
Lead UX designer and researcher
Engagement
About 6 months, 2016
Worked with
Product manager, 2 front-end engineers, RAN domain experts
Status
Shipped, in use

Problem

One base station holds dozens of hardware objects that serve GSM, WCDMA, and LTE at the same time. Engineers read its state from fault codes and command-line output, so their time went into working out which module, cable, or cell had failed before any repair could start.

What I did

I modelled how field engineers and NOC operators work, mapped the hardware and cell model, and designed the console. It has a runtime view of the whole site, one state language for every object type, a Cells view that separates cabling from cell mapping, and a commissioning wizard that checks each stage.

Outcome

The console shipped and is in use. Alarms appear on the module that raised them, and during commissioning the engineer can see which planned hardware is still missing or unconfigured.

01

The situation

D&M for SingleRAN (Diagnostics and Maintenance) is a browser console for Single RAN base stations, where one set of hardware serves GSM, WCDMA, and LTE at the same time. A site is a dense hierarchy of a cabinet, system and baseband modules, radio modules, mast-head amplifiers, antennas, fans, and power. All of it maps onto logical structures such as cells, channel groups, and antenna carriers. Each technology also reports to its own controller, the BSC for GSM, the RNC for WCDMA, and the EPC for LTE.

Two roles depend on the console. Field service engineers work at the cabinet with a laptop connected to the base station's local port, where they bring new hardware into service or replace a failed unit. Operators in the network operations centre (NOC) watch many sites remotely and decide whether an alarm needs a technician on site.

Before the console, the state of a site lived in text fault logs, command-line output, and the engineer's memory. An alarm arrived as an ID and a line of text, with no link to the module it came from or the cells it affected. People confused physical cabling with the logical mapping of cells, so they looked for faults on the wrong layer. Tools that were split by technology hid the shared hardware where many faults actually were.

Constraints

  • The screen shows what the base station reports. Every state comes from live telemetry over the local port or the backhaul, including the state of the optical and S1 links.
  • The plan lives elsewhere. The console can only show hardware as missing or unconfigured when the planned configuration is available from the network management system.
  • Licences and radio rules. Licence keys limit what an engineer can commission, and antenna tilt changes must follow regional rules on radio emissions.
02

Research and findings

I worked from three angles. I modelled how the two main roles work and where each loses time, analysed the hardware and cell model the console had to represent, and reviewed the text and command-line tools it would replace.

MethodFocusWhat it gave us
Role modellingField engineer at the cabinet, NOC operator working remotelyWhere each role loses time, such as comparing detected and planned hardware by hand, and deciding on a dispatch from a fault ID with no location
Domain analysisThe managed-object model, from cabinet to antenna carrierThe full object hierarchy, and the difference between physical cabling and logical cell mapping
Tool reviewFault manager, command-line tools, commissioning spreadsheetsState had to be relearned on every screen, and commissioning errors arrived late and mixed together

  1. Engineers think about a site the way it is wired

    Engineers reason module by module and link by link. A list can show each object's health, but it hides how objects connect, and a fault on one radio affects every antenna and cell that radio feeds.

  2. “Not working” covered three different situations

    In a log, a planned module that isn't installed, a module that is installed but not yet configured, and a module that has failed all look the same. Each needs a different action, and telling them apart decides whether a technician has to drive to the site. This finding gave Undetected and Uncommissioned their own states, separate from Failed, and it shaped the whole state language.

  3. Cabling and cell mapping were mistaken for each other

    A radio module is connected to the rest of the site by optical cables, and it also carries a mapping of cells and antenna carriers. People mixed up the two layers and looked for a fault on the wrong one.

  4. An alarm is only useful next to its object

    To decide whether to send a technician, a NOC operator needs to know which radio raised the alarm and which cells it feeds. A fault ID with a line of text gave neither.

03

Key decisions

1The site as a live map, with details for the selected object

The runtime view has three panels, with an object tree on the left, the site topology in the middle, and a details panel on the right. When the engineer selects a module on the map or in the tree, the details panel loads its information, parameters, faults, and KPIs, so every alarm appears next to the object it describes.

Set aside
A better fault list with columns for location and affected cells. It would still show each alarm on its own, without what the faulty unit is connected to.
Cost
The map becomes dense on large sites. A fault row names the problem and the module, but it doesn't suggest a fix.

2One state language for every object type

Seven states (normal, hover, selected, failed, undetected, alarms, and uncommissioned) look the same on a fan, a radio module, a cabinet, or a controller. Each state changes the icon, fill, or outline as well as the colour, so the main states don't depend on colour alone.

Set aside
A status label or badge on each object, like the fault list used. Engineers would have to read every label instead of scanning the site.
Cost
Seven states take time to learn. Failed, alarms, and undetected also had to stay distinct on small objects such as controllers and antennas, which needed a second, compact set of designs.

3Draw cabling and cell mapping differently

Physical links are solid lines and logical cell and antenna-carrier mapping is dashed. In the second version of the Cells view, cells became hexagons that list their receive and transmit antenna-carrier streams, and the main data stream got a label with its throughput and purpose.

Set aside
The first version, which drew cells as rectangles. Next to the radio modules and antennas, a cell looked like one more piece of hardware.
Cost
Two line styles and a new shape add visual weight to the busiest view in the console.

4GSM, WCDMA, and LTE on one map

The three controllers sit together on the left of the map. The cabinet, baseband, and radio modules they share appear once, and the header shows whether each technology is on air.

Set aside
A separate view for each technology, as in the earlier tools. Each view showed the shared hardware without the other technologies it serves, and faults on that hardware were hard to place.
Cost
The engineering teams for each technology had to accept one shared view of hardware they used to see on their own.

5Commissioning in stages, with each kind of error in its own tab

The wizard starts from the planned site. Objects stay hollow and serial number fields stay empty until the hardware is detected, and build actions such as adding a transport module sit inside the module they configure. Definition, relation, and hardware errors each have their own tab, and the wizard checks them at the stage where they arise.

Set aside
One check at the end. That is how parameter, relation, and hardware errors used to arrive, all at once and too late to trace easily.
Cost
The staged checks depend on the planned configuration being available from the network management system.

Reference for every object type

State language

  1. 1
    Hover and selected look different. A thin outline means the object can be selected. A strong blue outline means its details are open on the right.
  2. 2
    Failed uses red and a warning triangle. The fill, outline, and icon change together, so the state doesn't depend on colour alone.
  3. 3
    Undetected is hollow. A planned module that isn't there is drawn as an empty outline with grey ports, so it never looks broken.
  4. 4
    An alarm adds a bell. The module keeps its green dot because it still works, and the bell shows that there is an alarm to read.
  5. 5
    Uncommissioned shows a wrench. The hardware is installed but not configured yet, so it needs commissioning and nobody has to bring a spare part.
  6. 6
    The same states on every part. Cabinets, system and baseband modules, power, and fans all use them.
Field engineer at the cabinet

Commissioning wizard

  1. 1
    The site starts as Not commissioned. The header shows the commissioning state next to the BTS ID, so the engineer knows where the site stands.
  2. 2
    Errors sorted by kind. Definition, relation, and hardware errors each have a tab, so the engineer sees what kind of problem it is and where to fix it.
  3. 3
    The plan shows what's expected. Objects stay hollow and the serial number field stays empty until the hardware is detected.
  4. 4
    Build actions inside the module. The engineer adds the transport configuration on the module it belongs to, without switching to a spreadsheet.
05

Outcome

The console shipped, and engineers use it. Before handover, I reviewed the design against Nielsen's ten usability heuristics. It was strongest on visibility of system status, consistency, error prevention, and recognition over recall, because the map puts the structure of the site on screen where engineers used to keep it in their heads.

06

Reflection

  1. I would have timed the old workflow first

    The console was meant to make fault tracing faster and commissioning less error-prone, but I had no timed baseline from the text and command-line tools. A short timed test before the build would have let me show what the console changed in numbers.

  2. I would have designed for the largest sites from the start

    On large sites, crossing connection lines in the Cells view become hard to follow. Designing against the biggest real configuration early would have led me to group links and show detail on demand sooner.

  3. I would have designed the way back in the wizard with the way forward

    Commissioning changes live hardware, so engineers need to step back or cancel at every stage. The heuristic review showed the wizard had no clear undo, cancel, or back step, and I would have designed those controls alongside the forward flow.
