One live view of the whole base station.

Diagnostics & Maintenance for SingleRAN (D&M) is a browser-based console for Single-RAN base stations. It takes the tangle of a live multi-technology site (its system and baseband modules, radio units, antenna lines, and the data streams between them) and renders it as a single, stateful topology that a field engineer at the cabinet and an operator at the NOC (network operations centre) can both read at a glance.

Executive Summary

What the console does

A Single-RAN base station is a dense hierarchy of physical hardware (a cabinet, one or more system modules, baseband sub-modules, radio modules, mast-head amplifiers, antennas, fans, power) wired together and mapped onto logical structures (cells, channel groups, antenna carriers), running three generations of mobile technology at once.

Historically that complexity lived in text fault logs, CLI output, and the engineer's own memory of the site. D&M for SingleRAN puts it on one screen: a live topology where every object shows an unambiguous state, every physical and logical connection is drawn, and every alarm is shown on the module it came from. A guided wizard brings new hardware into service.

The core move
Draw the whole site as one live map.
Replace lists and log lines with a spatial, stateful graph that matches how engineers already think about a site, module by module and link by link. Going from "an alarm fired" to "this radio, on this cell, over this cable" then becomes a matter of reading the screen rather than working it out.

Problem Statement

Why the base station is hard to operate

Three properties of a modern base station make it hard to operate, and none of them are served by a flat, text-first tool.

Density
Dozens of objects, one chassis
A single cabinet can hold a system module, extension modules, several baseband sub-modules and a stack of radio modules, each with its own serial number, product code, ports and health. A list scrolls; it doesn't show how they connect.
Two kinds of connection
Physical ≠ logical
Cables and optical links (RP3/CPRI, S1) are one graph; the mapping of cells and antenna carriers onto radios is another. Engineers routinely misread one for the other, mis-locating faults.
Multi-RAT, concurrently
GSM, WCDMA and LTE at once
The same hardware serves three technologies with three controllers (BSC, RNC, EPC/MME). Tools that split by technology hide the shared hardware that faults actually live on.
Consequence
When state is invisible and relationships are implicit, the time goes into diagnosis (which module, which link, which cell?) and commissioning (does what's plugged in match the plan?), not into the repair itself. Both lean on tribal knowledge, and both are where site visits over-run.

Research Approach

How the design was researched

The design is reasoned from three things: how the two operator roles actually work, the structure of the SingleRAN hardware domain, and an evaluation against established usability heuristics. Every decision in the prototype traces to a specific friction in the text-and-CLI workflow it replaces.

  • Role modelling: the field engineer working at the cabinet and the operator triaging remotely from the NOC, and where each loses time today.
  • Domain grounding: the managed-object model (FSMF system module, FBBC baseband, RF modules, antenna line) and the two connection types, physical cabling and logical cell/carrier mapping.
  • Heuristic evaluation: the design assessed against Nielsen's ten usability heuristics (see §11), including its weaknesses.

Key Findings

What engineers need from the console

Finding 01
Engineers reason in topology, not in tables
The primary workspace is a node-and-link canvas, not a grid. The site is modelled as a graph because that is the mental model people already hold.
Visible in: Site & Cells view canvas
Finding 02
State must read at a glance, uniformly
A single visual language (colour, fill, outline, badge) is applied identically across every object type, so a green dot means the same thing on a fan as on a cell.
Visible in: 7-state element matrix
Finding 03
Physical and logical links must be distinguishable
Cabling and the cell/carrier mapping are drawn as different line treatments so a fault can be placed on the right layer.
Visible in: Cells view connections
Finding 04
"Not there yet" needs its own states
Undetected (planned, absent) and Uncommissioned (present, unconfigured) are separated from Failed. In a log the three look identical, but they need different actions.
Visible in: Undetected / Uncommissioned states
Finding 05
A fault is only useful when it's tied to its object
Faults, KPIs, parameters and info live in an object-scoped panel that follows selection, not in a detached global list.
Visible in: Details → Faults panel
Finding 06
Commissioning is knowledge-heavy and error-prone
Bring-up is staged, and its errors are split into definition, relation and hardware classes, showing what to fix and where the mismatch is.
Visible in: Commissioning wizard tabs

Design Principles

The principles behind the design

DP-01 · Topology is the primary object
The site is a graph you navigate. Details, faults and params are shown for whatever object you select on that graph.
Derived from: Finding 01 · Pain P04
DP-02 · One state language, everywhere
Colour, fill, outline and badge mean the same thing on every object type. Learn the grammar once; apply it to the whole site.
Derived from: Finding 02 · Pain P06
DP-03 · Draw both layers, keep them apart
Physical and logical connections are always both visible, but never rendered the same way. The distinction is the whole point.
Derived from: Finding 03 · Pain P02
DP-04 · Detail is object-scoped and one click away
Info, parameters, faults and KPIs follow the selected object. Context is never detached from the thing it describes.
Derived from: Finding 05 · Pain P01
DP-05 · Validate progressively, in place
Errors are classed and staged so problems are caught where they arise, not dumped at the end of commissioning.
Derived from: Finding 06 · Pain P05
DP-06 · Multi-RAT parity
GSM, WCDMA and LTE are shown as equals on shared hardware. No technology is a second-class citizen or a separate tool.
Derived from: Finding 01 · Pain P04

Heuristic Evaluation

Evaluation against usability heuristics

The design was evaluated against Nielsen Norman Group's ten usability heuristics. The console scores strongly on status visibility, consistency and error prevention. It also carries three weaknesses worth naming.

#HeuristicVerdictEvidence & gaps in the design
1Visibility of system statusStrongLive state dots, on-air / alarm / failed, throughput printed on the data-stream links
2Match to the real worldStrongTopology mirrors the physical site; nodes named as real hardware (SMOD / RMOD / PHYANT)
3User control & freedomGapNo visible undo / cancel / back in the wizard; commissioning needs a clear escape hatch
4Consistency & standardsSignatureThe seven-state visual language applied identically to every object type
5Error preventionStrongStaged wizard + definition / relation / hardware error classes; undetected vs uncommissioned
6Recognition over recallStrongThe topology shows the site's structure on screen, so engineers read it instead of recalling it
7Flexibility & efficiencyPartialObject-name and fault filters exist; explicit power-user shortcuts not yet surfaced
8Aesthetic & minimalist designRiskCells view is very dense; crossing connection lines are a real legibility risk at scale
9Diagnose & recover from errorsPartialFaults give ID + readable text + object scope, but no suggested corrective action yet
10Help & documentationScoped outNot present in these screens; deferred to a later release
Fix 1 · Add an escape hatch
Undo / cancel and a clear "back" at every wizard stage (heuristic 3).
Fix 2 · Tame density
Progressive disclosure and link-bundling to reduce the crossing-line overload in Cells view (heuristic 8).
Fix 3 · Suggest the fix
Pair each fault with a recommended next action, not just a description (heuristic 9).

Expected Impact

What the redesign was expected to change

The figures below are the design targets set going into build, reasoned from the specific frictions the design removes. They were never claimed as measurements: the right-hand column is the validation plan scoped alongside them.

Projected operational impact
Time to trace an alarm to its moduleminutes → one selection
Site commissioning time↓ ~20%
First-pass commissioning errors↓ ~30%
Avoidable truck rolls (better pre-dispatch triage)~15–20%
Mean time to repair↓ ~15–20%
Validation plan at handoff
Fault-localisationtimed task test vs the text/CLI baseline
Commissioningfirst-pass error rate + time-on-task, moderated
Usabilitytask success + SUS on the core flows
Field impacttruck-roll and MTTR tracking post-deployment
How the projections are grounded
These were conservative estimates, not measurements. They followed from the frictions the design removed: faster fault localisation means fewer wasted dispatches (a truck roll is sending a technician out to the site), and staged validation means fewer commissioning errors caught late. The figures were set at the low end on purpose, because the console improves visibility and pre-dispatch diagnosis, not predictive automation.
Platform alignment
The design's core bet, one browser-based console with one object model across all three RATs, matches the direction multi-RAT management tooling has taken since: a single interface unifying GSM, WCDMA and LTE operations instead of a separate tool per technology.

Dependencies & Constraints

What the console depends on

TECH
Live BTS O&M telemetry. Real-time object health, hardware detection and fault stream from the base station (local port or backhaul).
TECH
Fronthaul link status. RP3 / CPRI / OBSAI and S1 state to render physical connections and their up/down health.
DATA
Managed-object model. The full object taxonomy (cabinet → module → port → cell → carrier) that the tree and canvas are built from.
DATA
Network plan. Planned configuration from NetAct so the runtime view can overlay detected-vs-planned and drive Undetected/Uncommissioned states.
DATA
Fault dictionary. Stable fault IDs → human text mapping so alarm rows are readable and consistently attributed.
ORG
Field ↔ NOC workflow alignment. Both roles must trust one shared model; commissioning outputs must feed operations.
ORG
Per-RAT engineering teams. GSM/WCDMA/LTE ownership boundaries have to accept a shared-hardware, single-canvas view.
REG
Licensing & RF compliance. Feature/capacity license keys gate commissioning; RET tilt changes carry regional RF-emission constraints.
