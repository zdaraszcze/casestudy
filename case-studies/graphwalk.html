Case study, investigative graph analytics

GraphWalk: creating Virtual Paths without JSON, and finding saved work

Investigators lost time finding their own saved work, and only engineers could create Virtual Paths. I reorganised the Workspace around how investigations actually run, and designed a builder where investigators create paths by choosing sets and link types from named lists. The data model owner approves each path before it is published.

Role
Product designer
Worked with
Product manager, platform engineering, data model owner
Scope
Discovery to prototype, desktop web
Status
Clickable prototype, ready for usability testing

Problem

Investigators had hundreds of saved items in flat tiles, where urgent alerts looked the same as routine work. Virtual Paths could only be created by hand-writing JSON, and a mistake came back as a bare 400 error.

What I designed

I reduced the Workspace from seven flat sections to four areas, with sharing and defaults set by role. I also designed a path builder with live validation, cost warnings, and an AI shortcut, plus a review step where the data model owner publishes each path.

Expected outcome

No hand-written JSON to create a path, fewer path requests to engineering, and personal accounts instead of shared ones. All three still need to be measured in usability testing.

01

The situation

GraphWalk is an investigative graph analytics platform. Its main users are investigators, who move between four kinds of work: thematic reviews that take an hour, quick responses to alerts that take a few hours, data analysis over days, and long investigations that run for months.

The Workspace, where investigators keep and reopen saved work, was designed for a few items per user. Users now keep dozens to hundreds, and one user can have more than 80 link charts. Seven sections sit side by side with no priority, so a time-sensitive alert carries the same weight as a routine analysis. Search is the only reliable way to find anything. Teams keep spreadsheets of what they saved, and share accounts so they can see each other's work.

Virtual Paths are computed relationships across several sets, such as Transactions to Window data through Node. A saved path appears as a new link type in the Universe Viewer and Link Chart, and every user in the tenant sees it. There was no interface for creating one. Users wrote a JSON payload with raw set and link-type IDs, sent it to the REST API, and then updated permissions in a separate step that was easy to forget. Errors came back only after submission, as a 400 response with no guidance.

Constraints

  • One layout for every role. The requirements ruled out separate screens for each role.
  • No backend changes. The schema and the API contract were fixed, so every design had to produce the payload the API already accepts.
  • Desktop web only. Mobile, global navigation, and the Universe Viewer, Link Chart, Table View, Search, and Dashboard were out of scope.
02

What I found

I had no access to users in this phase, so I worked from the product itself. I reviewed the current Workspace and path creation against Nielsen's ten usability heuristics, worked through the product documentation, and checked each finding against Long Investigation, the workflow that runs longest and builds up the most saved items. Findings based on documentation rather than observation are marked Assumption.

  1. The four workflows belong to one person

    The four workflows looked like four personas, but the same investigator moves between all of them in a normal week. Supervisors, Presales, and Administrators share the same core actions and differ only in what they need to see first. Assumption

  2. Shared accounts were a workaround for missing sharing

    Shared accounts first looked like a bad habit. Teams used them because there was no other way to see a colleague's work. In investigative software, a shared account means the system can no longer show who opened or changed an item. That turned sharing from a nice-to-have into a core Workspace feature, and gave the project its clearest business case.

  3. Sets and link types already have names

    The Model Cloner refers to sets and link types by name, for example ${'People'-'part of'-'Criminal Organization'}. A name-to-ID mapping already existed, so a builder could let investigators pick by name without any backend change.

  4. Every saved path reaches the whole tenant

    So the approval step mattered more than the form. The flow had to settle who approves a path and what they need to see to judge it.

03

Key decisions

1One layout, with defaults set by role

Every role uses the same Workspace. Permissions from GET /api/v1/user/current decide what opens first.

RoleNeedsOpens on
InvestigatorReturn to recent work, see urgent alertsNeeds attention, Recent, own folders
SupervisorOversight of the teamTeam activity and alerts
PresalesDemos without live investigation dataFolders marked for demonstration only
AdministratorFolder, permission, and model controlPermissions and the path review queue
Set aside
A separate Workspace per role. Requirements ruled it out, and four layouts would mean four things to maintain for what is mostly one workflow.
Cost
The defaults depend on the permissions endpoint covering every rule. Platform engineering still needs to confirm this.

2Seven flat sections become four areas

The four areas are listed in order of how often investigators need them.

  • Alerts
  • Frequently used
  • Folders
  • Searches
  • Analyses
  • Link charts
  • Connecting set model
  1. Needs attentionAlerts, pinned at the top and hidden when empty
  2. RecentThe last items opened, to pick up where work stopped
  3. FoldersAnyone can create one and share it with named colleagues
  4. All itemsOne list with type filters, sorting, and readable names
Set aside
Keeping the seven sections and adding search filters. Search was already the only way that worked, and it does nothing for alerts or sharing.
Cost
Merging four item types into one list relies on users finding the type filters. This is the first thing the usability test will check.

3Build paths hop by hop, by name

Investigators pick a start set, then a link type and target set for each hop, from searchable lists. The builder checks each hop as it is added and draws the path on the graph, with a cost estimate, before saving. The builder produces the same JSON the API already accepts, and a JSON view stays in sync for technical users.

Set aside
A JSON editor with syntax help. It would be quick to build, but investigators would still need raw IDs. It survives as the optional JSON view.
Cost
A precise cost estimate needs a backend dry-run that does not exist yet. Until it does, the estimate uses set sizes and the number of hops.

4The data model owner approves new paths

Each path has a visible status: Draft, In review, Returned, or Published. Investigators submit a proposal, and the model owner publishes it or returns it with a note. Publishing sets the path's permission in the same action, which removes the step users used to forget. Editing a published path creates a new draft, so analyses that use the live version keep working.

Set aside
Supervisor approval, which my first version of the flow relied on. Supervisors manage people and cannot judge whether a path is correct or affordable. I also set aside direct publishing for everyone, which would let any user change the model for the whole tenant.
Cost
Investigators have to wait for review, so status labels and notifications keep them informed. Who may publish without review is a product and compliance decision. The life cycle supports either policy.

5AI as a shortcut into the builder

Building a multi-hop path is hard even with a builder, so investigators can also describe the relationship in plain language. AI proposes a path using only sets and link types that exist in the tenant, and the proposal opens in the builder for the same checks.

Set aside
AI as the only way to create paths. Creation would stop whenever AI is unavailable or wrong.
Cost
It depends on AI usage limits that are not confirmed yet, so the builder works without it.

The design

The creation flow has two checkpoints: validation before anything reaches the backend, and review before anything reaches other users.

Administrator, data model owner

Paths and review

  1. 1
    Review queue for the model owner only. Other roles see My paths and Published. The count shows how many proposals are waiting.
  2. 2
    Status always visible. Every path is a draft, in review, returned, or published. A returned path shows the reviewer’s note and opens in the builder for changes.

05

Outcome and validation

The design is a prototype and has not been tested with users. These are the outcomes I expect. Each one would be measured twice with the same tasks, first on the current application for a baseline and then on the prototype.

OutcomeMeasureWho benefits
No hand-written JSONLines of JSON written to create a path, and first-attempt success rateInvestigators
Faster return to workTime to find and open a saved itemInvestigators
Less engineering loadPath requests sent to engineering and solution engineersEngineering
Paths that get usedShare of published paths used in an analysis within 30 daysProduct team
Auditable accessShared accounts per tenantSecurity and compliance

Validation plan

I would run moderated sessions with five investigators, using Long Investigation and Quick Response scenarios on the current application and then on the prototype. Short interviews in the same sessions would test the assumptions in Section 02. The first two things to check are whether investigators find the type filters in All items, and whether they can build a two-hop path without help.

06

Reflection

  1. I would put the design in front of investigators sooner

    Every user insight here is based on documentation. Five short interviews before the decisions would have tested the idea that one investigator does all four kinds of work, which the whole layout rests on.

  2. Governance should have come first

    My first flow sent proposals to supervisors. Asking who could actually judge a path moved review to the model owner and changed what the builder had to show: the cost estimate and validation now serve the reviewer as much as the author.
