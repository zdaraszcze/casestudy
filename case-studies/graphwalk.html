Executive Summary

This exercise covers two GraphWalk redesign tasks — the Workspace (Task 1) and the Virtual Path authoring UI (Task 2). Both briefs share one objective and the same constraints, so they are treated as a single design problem addressed through a shared principle rather than a functional dependency. The primary user is the Investigator / Operational Analyst, whose work spans four workflows of very different durations. Every figure below is drawn from the brief, product documentation, and the provided screenshots; interpretations that still need validation are flagged as assumptions.

Proposed Direction

One dataset, presented through role-driven views controlled by permissions — not four separate screens. Each role gets a default view plus a set of available filters and columns. Raw IDs are replaced by name-based selection throughout. Virtual Path creation moves into a guided builder with live validation, a path preview, and performance warnings, gated behind a review model appropriate to the role. AI is applied only where it removes a specific friction, not as decoration.

Decisions for Review

Hard Constraint

No Separate Screen Per Role

The brief rules out four separate screens. Role-awareness is delivered through conditional rendering over one layout, gated by permissions — not by building a distinct Workspace per persona.

Governance Decision

Authoring Is Gated Behind Review

Because a Virtual Path is tenant-wide, unrestricted authoring is excluded intentionally. The open design question is the review model (direct / proposal-and-approval / role-based gating), not whether authoring is possible.

01

Problem Statement

Task 1 · Workspace

The Workspace is the investigator's home for saved work. Its tile layout was designed for a small number of items per user. Users now retain dozens to hundreds of items, which makes browsing impractical and forces reliance on search. The layout provides no visual hierarchy: time-sensitive alerts appear alongside routine analyses and link charts, and sections grow without limit — for example 80 or more link charts per user. Teams compensate with external spreadsheets and shared accounts.

Sections observed: Folders, Frequently used, Connecting set model, Searches, Alerts, Analyses, Link charts.

Task 2 · Virtual Paths

A Virtual Path is a computed relationship that appears as a new link type on the Universe Viewer and Link Chart. The feature exists only on the backend. Creating a path currently requires a hand-written JSON payload with raw set and link-type IDs, followed by a separate, easily-forgotten permission update. Validation occurs only after submission — the API returns a 400 error with no in-form feedback and no path preview. Because a path is a model-level object, anything created through the UI affects the entire tenant's model.

Creation today is possible only through the REST API or the Model Cloner.

The Shared Design Question

How can a powerful, technically-shaped feature be made approachable to the Investigator without reducing its capability — presenting one dataset through role-driven views rather than a separate layout per persona, while keeping a tenant-wide model object safe to author?

Shared Objective

Both briefs share one objective: make a powerful, technically-shaped feature approachable without reducing its capability. Fact

Shared Constraints

Role-aware behaviour without a separate screen per role; backend and data model unchanged; the API contract is fixed; desktop only. Fact

03

Key Findings

01

The core workflow is common; role needs are narrow

Locating, opening, and organising saved work accounts for roughly 80% of the value and is common to all roles. Role-specific needs are narrow: the Supervisor needs an oversight view; Presales needs author and last-modified metadata plus demo-safe presentation; the Administrator needs folder and permission governance. Decision

Implication: each role receives a default view and a set of available filters and columns, controlled by permissions — not a separate layout. This satisfies the constraint that four separate screens are not acceptable.

02

The tile layout collapses under real item counts

Sections grow without limit and carry no hierarchy, so the interface can't distinguish a time-sensitive alert from a routine link chart. Users fall back on search, external spreadsheets, and shared accounts to cope. Fact

A high-impact, low-cost change is letting end users create their own folders, removing the administrator bottleneck.

03

A name-to-ID mapping already exists

The Model Cloner already references sets and link types by name, for example ${'People'-'part of'-'Criminal Organization'}, rather than raw IDs. A name-to-ID mapping therefore exists, so the UI can let the user select by name and keep IDs as metadata. Decision (per docs)

This is the foundation for removing raw IDs from both the Workspace tiles and the Virtual Path builder.

04

The tile badge is undefined — it stays an assumption

Each tile carries a numeric badge, and the same number appears under different sections (e.g. under Alerts and under Analyses). The documentation does not define the badge, so its meaning — and whether one item can appear in several sections — stays an open assumption rather than a resolved decision. Assumption

User Flow — Guided Create-a-Virtual-Path

The task-level flow for authoring a Virtual Path, from intent in the Universe Viewer to a saved, usable path. It shows the two decision forks that make this feature safe and approachable: validation before commit (nothing reaches the backend blind), and review-gating by role (a tenant-wide object is never published without the appropriate oversight). Rectangles are screens/actions; diamonds are decisions; the green terminus is a usable path.

Fork 1 — Validate before commit

Live, in-form validation replaces the post-submit 400. The user never reaches a dead end; errors are fixed in place with a suggestion.

Fork 2 — Gate by role

A permitted role saves directly (path + permission in one action). Others submit a proposal to supervisor review — a tenant-wide object is never published without oversight.

AI is an on-ramp, not the road

The "describe it" entry produces a proposed path the user reviews and edits on the graph, then rejoins the same validated flow. The builder works fully without it.

Design Principles

01

One dataset, role-driven views

The same Workspace serves every role. Difference is expressed as a default view plus available filters and columns, gated by permissions — never as a separate screen per persona. Complexity is the platform's job, not the user's.

Derived from: the shared constraint (no separate screen per role) and the finding that ~80% of the workflow is common.

02

Select by name, never by raw ID

Users choose sets and link types by human-readable name with autocomplete; IDs are retained silently as metadata. Technical namespace::set labels move to a tooltip. This holds in the Workspace and the Virtual Path builder alike.

Derived from: the existing Model Cloner name-to-ID mapping and the brief's explicit requirement to select sets by name.

03

Validate before submit, preview before commit

Feedback happens as the user builds, not after a failed submission. Before a path is committed, it is rendered on the graph and its cost estimated, so the user confirms it is both correct and useful. The silent 400 disappears.

Derived from: post-submit-only validation and on-demand path cost as documented pains.

04

Author with guardrails, not by removing them

Because a Virtual Path is tenant-wide, the goal is to enable authoring safely — through a review model matched to the role — not to open unrestricted editing of the model. Guardrails are part of the feature, not a barrier bolted on afterwards.

Derived from: the model-level-object constraint and the explicit exclusion of unrestricted authoring.

05

AI proposes; the investigator decides

AI is applied only where it removes a specific friction — turning a natural-language request into a proposed path to review on the graph. It is a supporting on-ramp, never the primary solution, so it cannot mask weaknesses in the core experience.

Derived from: the risk that over-reliance on AI could mask core-experience weaknesses.

Dependencies, Scope & Open Questions

Each item is a dependency to resolve before build, or a question requiring a product decision. Grouped by type. Below them, the explicit scope boundaries and deliberate exclusions carried from discovery.

System / API Dependencies

SYS
Pre-commit path cost / dry-run

Paths are calculated on demand. A true performance estimate before commit depends on backend support for a dry-run or feasibility check. If unavailable within the fixed API contract, the warning degrades to a heuristic (set sizes × hop count). Owner: Platform / Backend.

SYS
Role-based rendering via existing endpoints

Conditional views rely on identity and permissions already exposed by GET /api/v1/user/current and /api/v1/permission/update/user/{userId}. Confirm these cover every view/column gating case needed. Owner: Platform.

SYS
AI assist feasibility

Are there system limitations that would prevent an AI assist for search or Virtual Path creation, or conversational graph search surfacing correlations between related entity sets? To confirm before scoping the AI on-ramp. Owner: Platform / Data Science.

Model / Governance Dependencies

MODEL
Virtual Path review model

A path is tenant-wide, so the authoring/review model must be chosen: direct (fast, higher risk), proposal + supervisor approval (safer, slower), or role-based gating. This is the central open product decision for Task 2. Owner: Product + Compliance/Governance.

MODEL
Permission coupling on save

Today authoring requires a separate, easily-forgotten permission update. The design couples permission into the save action; confirm the permission-update endpoint can be invoked transactionally with path creation. Owner: Platform.

Data / Definition Questions

DATA
Numeric tile badge — undefined

The badge is not defined in documentation, and the same number recurs across sections. Determine what it represents and whether one item can appear under more than one section, before the tile is finalised. Owner: Product. Assumption

DATA
"Group by category / author" behaviour

Does this reshape the existing tiles, or query the database and render a data grid? The answer changes the Workspace interaction model. Owner: Product + Backend.

DATA
Empty-section & add-item behaviour

How does an empty section behave, and how does a user add items to a section? Not shown in the screenshots. Owner: Product.

DATA
Workspace as first screen & Universe Viewer effects

Confirm the Workspace is the first screen after login (consistent across roles), and whether Universe Viewer actions generate new data, sections, or items in the Workspace. Owner: Product.

Organisational / Role Questions

ORG
Cross-role functionality overlap

Is there any case where one role requires another role's functionality within its own view? Documentation indicates minimal overlap, but edge cases must be validated before the single-layout approach is locked. Owner: Product + Research. Assumption

Scope Boundaries

In Scope
  • Task 1: the Workspace screen and selected flows — filter, sort, open, organise, share, alerts. Web, desktop, role-aware behaviour.
  • Task 2: the create-Virtual-Path flow from intent to a saved, usable path; edit and manage; path visualisation; validation feedback; power-user vs guided creation.
Out of Scope
  • Universe Viewer, Link Chart, Table View, Search, Dashboard — unchanged. Backend and data-model changes excluded; the API contract is fixed.
  • Mobile and responsive design. Full navigation redesign — the left rail and top tabs remain unless a change is essential.
